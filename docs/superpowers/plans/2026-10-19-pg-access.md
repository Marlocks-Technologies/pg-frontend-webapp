# PG Access Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Gate all PG app and API access behind Cognito, with ten accounts, two admins, and three enforced roles.

**Architecture:** Cognito owns authentication; a DynamoDB registry owns enabled state, role, and capacity. Next.js holds the browser session and forwards authenticated REST requests. API Gateway authenticates REST calls, a WebSocket authorizer authenticates connections, and Lambda enforces roles and resource ownership.

**Tech Stack:** Next.js 15, TypeScript, Auth.js/Cognito OAuth PKCE, Python Lambda, DynamoDB, Terraform AWS provider 5.x.

**Spec:** `../specs/2026-10-19-pg-access-and-usage-design.md`

## Global Constraints

- Ten enabled accounts maximum; invitations occupy slots.
- Two enabled admins maximum; last admin cannot be demoted or disabled.
- Roles are `admin`, `document_manager`, `regular_user`.
- No public signup; no password handling by the app.
- Health and CORS preflight remain public; all data operations require identity.
- Existing unowned chat history is unavailable until assigned to an owner.

## Review Focus

- Concurrent invitations at the ten-account boundary must produce exactly one winner.
- Demoting or disabling the last admin must fail.
- A regular user calling upload directly must get 403 even if the UI hides the button.
- A guessed session or research-job ID must not reveal another person's content.
- A valid JWT for a disabled account must be rejected.
